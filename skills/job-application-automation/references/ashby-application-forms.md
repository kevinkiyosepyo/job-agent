# Ashby Application Forms

## Verified completion pattern

Use for official `jobs.ashbyhq.com/.../application` forms.

1. Open the direct `/application` URL and wait for the dynamic form to replace the **Fetching application form** state before inventorying or filling.
2. Upload the exact resume and any required supporting document with `DOM.setFileInputFiles`; re-read both `input.files[0].name` and the rendered filename. With a CDP worker that reattaches on every command, `nodeId` is session-local: do not reuse it across attachments. Use the same attached session for the whole operation, or obtain the exact input's `backendNodeId` from `DOM.getDocument` and pass `backendNodeId` to `DOM.setFileInputFiles`. A stale-node error is not a file-picker problem.
3. For React-controlled required text fields, do not accept a DOM value alone as proof. Enter the final value with trusted browser keyboard input (focus field, clear it, then `Input.insertText`), because synthetic DOM value assignment plus input events may look correct but fail Ashby server-side validation.
4. Inspect every required choice control. Ashby can mix radio groups, checkboxes, and button-backed `data-field-path` controls. Use trusted page mouse input on the exact rendered radio label or `button[data-option='yes'|'no']`; reacquire geometry and verify the hit target before clicking. Do not infer that earlier similarly worded questions cover later fields.
5. **Wait for saved state, not only selected styling.** Radio `checked`, button `aria-pressed`, and a screenshot can all show the right answer while Ashby's saved form value is still missing. Complete each field's asynchronous save before moving on. Where observable, inspect the nearest field component's read-only `savedValue` for the exact field path and require it to match the actual option value; an explicit boolean `false` is a valid saved No, while `undefined` is missing. Do not mutate framework state, call private save handlers, or normalize option values to guessed IDs/strings. Ashby option values can contain a leading space absent from the rendered label.
6. If a choice is visibly selected but its saved value is absent, use trusted input to clear and reselect the **same truthful option**, then verify saved state and error clearance. Do not trial a different legal/consent answer or change validity flags. In a verified Rivian/VW case, this restored three missing saved values and the subsequent authorized attempt succeeded.
7. Submit once only after all required fields, exact resume, saved selections, and rendered validation are verified. Read back explicit confirmation such as `Your application was successfully submitted.` Do not open or update the Sheets tracker unless Kevin explicitly requests it. Preserve submit intent and inspect without replay after an uncertain outcome. After a definitive validation rejection, any additional Submit requires explicit user authorization for that retry; retain the original attempt record and verify all repairs before consuming the new authorization.

## Verified control mechanics (CDP)

Learned across four confirmed Ashby submissions (fab2 ×3, Replit). These are the failures that cost the most retries:

- **Cmd/Ctrl+A does not select-all in these React inputs.** `Input.dispatchKeyEvent` with `modifiers=4` (Ctrl) or `8` (Cmd) leaves the existing value in place, so `Input.insertText` *appends*. The visible symptom is catastrophic and easy to miss: every later value concatenates into one earlier field (observed: name doubled, and the blurb + end date both landed inside "Ideal start date"). Clear with the native value setter first — `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set` called with `''` plus bubbling `input`/`change` events — then click the field and type the real value with trusted `Input.insertText`. Read the value back after every write.
- **Never resolve a field by label substring alone.** "Ideal start date" is a prefix-match for the group that also matches "Ideal end date" queries in some orderings. Inventory `[data-field-entry-id]` once, record the **index** of each question, and fill by index; keep label matching only for a first pass.
- **Location is an autocomplete combobox, not free text.** Typed text never saves and Ashby rejects the form with `Missing entry for required field: Location`. Type a prefix, wait for the listbox, then click the real suggestion (e.g. `San Diego, California, United States`) and verify the bound value.
- **Date questions are `react-datepicker` inputs.** Prose like "June 14, 2027" is discarded. Type `MM/DD/YYYY`, then dispatch Enter to commit the picker, then read the value back.
- **Fields rendered without a visible `*` can still be server-required.** fab2 rejected both `Location` and the conditional "If no, is your home country listed below?" even though the DOM heading showed no asterisk. Treat the server's rejection list as authoritative and answer every question truthfully rather than trusting the rendered required flag.
- **Invisible reCAPTCHA v3 is not a gate.** A `grecaptcha-badge` plus zero-size/hidden `recaptcha` iframes is a dormant background integration. Gate the submit only on a *visible* challenge widget (width/height > 4, not `display:none`/`visibility:hidden`, class not `grecaptcha-badge|logo`) or literal challenge text ("I'm not a robot", "verify you are human"). A naive `querySelector('iframe[src*="recaptcha"]')` check blocks every Ashby submission for no reason.
- Confirmation text differs per org — fab2 returns "We'll contact you with feedback soon.", Replit "We'll contact you if there are next steps." Match on `successfully submitted` and additionally verify the form is gone (`[data-field-entry-id]` count is 0 and the Submit button no longer exists).

## Complete form inventory and pre-submit checks

1. Inventory all `[data-field-entry-id]` groups, their visible question labels, text/file inputs, radio groups, checkboxes, and pressed buttons. Do not restrict the audit to `.ashby-application-form-field-entry`: some radio groups use different wrappers and would be silently omitted.
2. Do not assume a `<form>` exists. A verified Ashby page had `document.forms.length === 0`. An empty form-validity list is **not a pass**. Inspect individual input/textarea/select validity, required question headings and choice groups, visible alerts, and each required field's saved value.
3. For text, focus and select the exact field, use trusted `Input.insertText`, then blur and read back. Preserve already correct values instead of appending or refilling indiscriminately.
4. For choices, identify the exact option by its rendered label. Scroll only that target into the viewport; reacquire its rectangle and check `document.elementFromPoint` hits the target/associated label before trusted page mouse press/release. This is background browser input, not a native OS click or foreground focus change.
5. Wait with bounded state polling after **each** answer. Require the intended selection plus an observable saved value and completion of its pending save. React field `savedValue` is read-only diagnostic evidence, not a stable public API: rediscover the exact field path, do not hardcode minified component names, and do not rely on a stale alternate fiber alone. If saved state cannot be observed reliably, seek an authoritative saved-step/server read-back rather than silently declaring the field verified.
6. Distinguish display labels from exact option values. A real Rivian option's saved string began with a space that its rendered label did not show. Read the actual option/saved value before asserting exact equality. If an assertion differs only because the expected value was wrong, fix the assertion—not the already correctly saved answer. Never trim or fabricate identifiers/values sent to the ATS.
7. Confirm the exact profile-selected resume file object **and** rendered filename, every required group, unchanged legal/consent answers, no visible errors, and one enabled Submit button. Use a screenshot/vision pass to catch layout or selection mistakes, but never substitute the screenshot for saved-state verification.

## Recovery and evidence

- If Submit yields `Your form needs corrections` or `Missing entry for required field`, record the exact rejection and do not call the application submitted. Compare the named fields' visible selections with their saved values before choosing a repair.
- A selected-but-unsaved choice is a distinct failure from an incorrect answer. Clear and reselect only the same truthful option with trusted input; wait for its saved value and error clearance. Do not change sponsorship, citizenship, prior employment, or optional consent to a false answer as a test.
- Retain the first attempt and any separately authorized retry as separate durable records. A definitive rejection plus explicit user retry authorization is different from an uncertain spinner/timeout; never automatically replay an uncertain submission or discard its intent record.
- After an authorized submission, perform a fresh read of the exact target. Require explicit success text and inspect remaining errors/Submit controls. Save the observed confirmation, exact role/URL, timestamp, and resume basename; do not invent an application/reference number.
- Send the completion notification only after portal confirmation, then read back the exact delivered Discord message. Keep Sheets untouched unless explicitly requested.
